
#### Impacto no migration history se este rollback for usado

Este rollback aplica SQL diretamente (`db query -f`), não via `supabase
migration repair`/nova migration. Isso significa:

- executar este rollback manualmente reverte o schema (policies e grant
  voltam ao estado anterior);
- o histórico remoto de migrations (`supabase migration list`) **ainda
  poderá marcar** `20260806120000_harden_gifts_delivery_read_access.sql`
  como aplicada — o rollback SQL não desfaz a entrada no histórico;
- nessa situação, **não executar outro `supabase db push`** — o histórico
  remoto e o estado real do schema estarão divergentes;
- **parar e reconciliar formalmente o histórico de migrations antes de
  qualquer reaplicação** — a reconciliação (ex.: `supabase migration
  repair`) deve ser revisada separadamente, numa etapa própria, e não
  tomada como parte automática deste runbook;
- não apagar nem editar a migration `20260806120000` já aplicada;
- em Produção, se o hardening já tiver sido incorporado ao histórico
  oficial (migration aplicada e mergeada), preferir uma **migration
  corretiva futura** a reverter/editar o histórico existente.

Não há, neste runbook, nenhum comando de `migration repair` — isso é
proposital: essa decisão exige revisão específica de quem estiver
conduzindo a reconciliação, não deve ser executada mecanicamente.
